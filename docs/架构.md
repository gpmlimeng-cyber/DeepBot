# 架构：三层各归其位

```
┌──────────────── 本仓库（DeepBot 壳）────────────────┐
│ app/          Android 工程：WebView 宿主、注入、主题、  │
│               安全区、壳设置页、原生能力                │
│ runtime/      引擎运行时的组装与安卓补丁               │
│ scripts/      构建与取件脚本（build-apk / fetch-dsbot） │
│ docs/         本文档                                │
│ versions.env  唯一版本真源                            │
└───────────────┬──────────────────┬──────────────────┘
                │ npm 版本 + sha512 │ commit
        ┌───────▼────────┐  ┌──────▼─────────────┐
        │ 官方上游引擎     │  │ 我们的 ds-bot 二开仓 │
        │ @deepseek-ai/dsh│  │ gpmlimeng-cyber/…  │
        └────────────────┘  └────────────────────┘
```

**为什么要分成三层**

1. **引擎不 fork**：官方 npm 包按版本引用，升级只改 `versions.env` 一行。
   fork 引擎的代价是每次上游更新都要跟一次合并，而我们没有任何引擎侧的独占需求
   （所有安卓适配都在 `runtime/` 的补丁里，打在上游产物上、可幂等重放）。
2. **ds-bot 不复刻**：直接引用我们二开仓库的 commit，仓库里不留源码副本。
   两处真源必然打架——改了仓库里那份、忘了推上游，问题会以"只有某些包有问题"的形式出现。
3. **壳是本仓库**：这是唯一我们独占、且需要精细控制的部分（WebView 注入、状态栏、
   安全区、原生能力桥、壳设置页）。

**依赖边界**

- 壳 → 引擎：HTTP（127.0.0.1）+ 进程管理，无源码级耦合。
- 壳 → ds-bot：只通过注入 CSS/JS 与一个 JS 桥（`DeepBotShell.openSettings()`）交互，
  不读它的源码、不改它的文件。
- 引擎 → ds-bot：官方插件机制（`dsh.client` + cordis patch），升级引擎不覆盖插件。
